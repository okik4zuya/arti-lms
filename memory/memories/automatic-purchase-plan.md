## Architecture
1. **orders** table (uuid, `public_id` random for URLs, email, name, whatsapp, `type` purchase|renewal, `amount`, `price_tier` launch|normal, `launch_slot` nullable unique, `status` pending|paid|fulfilling|fulfilled|failed|expired|refunded|needs_attention, gateway name/ref/payment method, `paid_at`, `expires_at`, `license_issuance_id`, `user_id`, `fulfilled_at`, per-stage timestamps `email_sent_at`/`whatsapp_sent_at`, `refunded_at`/`refund_reason`). Webhook payloads are stored with keys and card data stripped; no password and no key in any log.
2. **Checkout** (`POST /beli`, throttle `checkout`): validate name/email/whatsapp, reuse an open pending order for the same email, reserve the price inside a DB transaction, create the gateway transaction for exactly that amount, redirect to the gateway page; `GET /beli/selesai/{public_id}` is the success page ("cek email", no key, no status leak beyond paid/pending).
3. **Atomic launch quota:** a `launch_slot` column with a unique index, 1..100. Assigned in a transaction that takes `lockForUpdate` on a one-row counter (or on the orders table range) and picks the lowest free slot; a pending order holds the slot until its `expires_at`, an expired/failed order frees it. Two simultaneous payments cannot both get slot 100 (unique index is the backstop). The displayed "sold" count = manual offset (`SITE_LAUNCH_SOLD`, for sales done by WhatsApp before this) + orders with a slot that are paid. Late payment after expiry: if the amount equals the order amount it is still fulfilled at that price when a slot is free, otherwise `needs_attention` (admin decides; money is already taken).
4. **Webhook** `POST /webhooks/pembayaran` (Laravel; verify signature in constant time; then re-read the transaction status from the gateway API before trusting it; compare `gross_amount` to `orders.amount`; `status` transition is a compare-and-set `UPDATE ... WHERE status IN (pending, expired)`; respond 200 on duplicates). Dispatches `FulfillOrder` after commit.
5. **FulfillOrder** (queued, unique per order, 5 tries with backoff) in resumable stages, each stored on the order so a retry skips finished work: (a) `CreateLearner` (existing email = reuse account, never touch its password), (b) `IssueLicense` with `order_ref = order public id` (Worker is idempotent on it), (c) set-password link, (d) email (queued separately, failure does not fail the order), (e) WhatsApp (own job, optional, failure only recorded). Same order cannot issue two keys: unique `order_ref` locally and at the Worker; the job is `ShouldBeUnique`.
6. **Set-password link:** two password brokers on the same `password_reset_tokens` table: `users` (60 min, forgot-password) and `welcome` (default 48 h, from purchase). The reset route is `GET /atur-sandi/{token}` inside a **signed** URL whose query carries `email` and `b=welcome|users`, so the lifetime cannot be switched by editing the URL; the broker deletes the token on success (one-time). The token itself is created with `createToken`, so purchase links do not trip the 60 s broker throttle. Password is never sent, stored, or logged; mail/WhatsApp/Filament contain only the link.
7. **Forgot password:** `GET/POST /lupa-sandi`, `GET/POST /atur-sandi`; uniform answer for known/unknown/admin emails; named limiters per IP and per email; queued Brevo mail; rules `Password::min(10)->letters()->numbers()` plus not equal to email; after reset rotate `remember_token`, add `AuthenticateSession` to authenticated routes and call `logoutOtherDevices` equivalent so other sessions die; no auto-login (go to login with a status line). Admin/support addresses get the same uniform answer but no mail is sent (question 3).
8. **WhatsApp stage:** `WhatsAppSender` interface with drivers `log` (default, also in tests), later `cloud` or `fonnte`; message built by the existing template with `{account}` replaced by the set-password link; stage failure never fails the order; admin sees status and can resend from Filament.
9. **Refund:** admin action on an order: marks `refunded`, calls `RevokeLicense`, removes course access, logs an event; the money is returned in the gateway dashboard (no gateway refund API call in v1).
10. **orders:reconcile** (scheduled every 10 min plus manual): for `pending` orders older than 5 min and not expired, ask the gateway for status; paid -> same code path as the webhook; also re-dispatches orders stuck in `paid`/`fulfilling` and sends the admin a mail for `needs_attention`.
11. **Filament** `OrderResource` (admin + support read, admin refund/mark/resend, filters, link to the license row, event timeline, no key or token shown).
12. **Renewal** (year 2, Rp199.000): `type=renewal` order started from `/app` by a logged-in learner whose license is within 30 days of expiry or expired; fulfilment calls `ExtendLicense` with `order_ref`; **blocked on the Worker `extend` accepting `order_ref`**. A reminder mail 30 days before expiry (scheduled, off by default).
13. **Worker spec to hand over** (other repo, not touched): (i) `POST /admin/resend` accepts `silent: true` and then sends no email, returns the new key; (ii) `POST /admin/extend` accepts `order_ref` and is idempotent on it (second call with the same `order_ref` returns the first result with HTTP 200 and `replayed: true`, no second extension; a different license with the same ref -> 409). Tests: replay returns same expiry, concurrent double call extends once, missing `order_ref` keeps old behaviour, `silent` writes no `email_outbox` row.

## Answers 2026-10-18
- Gateway = **Xendit** (researcher has no NIB, registers as an individual). Planned: Invoice API (hosted page, QRIS/VA/e-wallet), `x-callback-token` check plus a GET of the invoice before trusting it.
- **Gateway update 2026-10-18 (later):** Xendit turned out to require a NIB for the researcher; Midtrans researched. Midtrans' own docs ("What are the legal documents required...") list for a domestic **individual** account: owner's KTP and NPWP, **no NIB** (NIB/SIUP/TDP only for company and foundation accounts). Third-party guides disagree on NPWP (some say KTP is enough for QRIS, VA and GoPay and NPWP is only for cards). The bank account for an individual must be in the owner's own name. Individual and company accounts differ in the payment methods available (the comparison is an image in the docs, not readable). Website criteria: active site, clear product info, prices in IDR; prohibited businesses are scams, adult, gambling and similar (courses and software licences are not named either way). Sandbox is available at once; card activation can take about 10 working days. Midtrans support should confirm NPWP and the QRIS, VA and e-wallet methods for the individual account. The code is Xendit-specific (`XenditClient`, `SettleInvoice`); a gateway interface with a Midtrans Snap driver is the next build if the researcher confirms Midtrans.
- Product direction: **one-time, lifetime purchase** instead of Rp199.000/year (product adapts later). Consequences recorded: no renewal order type, no reminder mail, Worker `extend order_ref` no longer needed (only `resend silent`), no course-access expiry question, and every "per tahun / satu tahun / Rp16.600 per bulan / setelah satu tahun" claim on the landing, `/syarat`, series mail 4 and tests must be reworded. Price and the meaning of "lifetime" still to be answered.
